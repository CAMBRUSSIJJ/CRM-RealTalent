# RealTalent CRM V100.52.0 — Architecture & Production Hardening

## Objetivo

A V100.52.0 é uma release de estabilização. O foco é remover riscos silenciosos de produção, melhorar a consistência dos dados e preparar o CRM para crescimento sem reescrever a aplicação.

## Mudanças críticas

### 1. Build de produção protegido

- `npm run build` agora executa `validate:env` antes do Vite.
- Builds hospedados no Vercel exigem `VITE_DATA_MODE=supabase`.
- O modo local continua disponível para desenvolvimento e demonstração.
- O build principal volta a ser responsabilidade do Vite; o builder antigo foi preservado em `npm run build:legacy` somente como contingência.
- React, ReactDOM, Lucide e Supabase JS deixam de depender de `esm.sh` no build principal.

### 2. Typecheck real

- `npm run typecheck` agora executa `tsc --noEmit`.
- A auditoria sintática anterior permanece disponível em `npm run syntax:audit` e agora também falha quando um import relativo aponta para um módulo inexistente.
- Foi corrigido um import quebrado pré-existente em `call-session-config.ts`, que apontava para um módulo inexistente dentro de `features/calls`.
- O pipeline `npm run check` combina sintaxe, integridade das migrations, TypeScript, testes e build.

### 3. Paginação segura do Supabase

- Consultas de entidades centrais usam ranges de 1.000 registros e deixam de confiar no `max_rows` do PostgREST.
- Existe um limite explícito de segurança de 50.000 registros por entidade durante snapshots completos.
- A paginação possui testes unitários próprios.
- A migration V100.52 adiciona índices alinhados com a ordenação das consultas paginadas.

Entidades cobertas: leads, empresas, contatos, oportunidades, perfis sociais, etapas, atividades, agenda, playbooks, produtos, propostas, itens de proposta, receita, metas e regras de automação.

### 4. Realtime incremental

Eventos Realtime não recarregam mais todo o snapshot do CRM indiscriminadamente. Cada tabela atualiza somente o slice correspondente, com debounce por domínio.

Também foram adicionadas subscriptions para entidades comerciais e financeiras que antes podiam ficar defasadas na interface.

### 5. Política central de “Não entrar em contato”

A nova `contact-policy` é a regra única para contatos manuais. Ligações, WhatsApp, e-mail e Instagram deixam de abrir quando o lead está bloqueado. Cadências também ignoram leads marcados como “Não entrar em contato”.

A engine de automação local e o `automation-runner` do Supabase também ignoram eventos associados a leads marcados como `doNotContact`/`do_not_contact`.

### 6. Identidade local consistente

O identificador de usuário do modo local foi normalizado para `local-user`. Isso elimina divergências entre owner, member e autenticação em workspaces locais.

### 7. Navegação persistente

A rota atual passa a ser refletida no hash da URL (`#/leads`, `#/pipeline`, `#/agenda`, etc.). Com isso:

- F5 preserva o módulo aberto;
- voltar/avançar do navegador funciona;
- URLs internas podem ser copiadas sem exigir uma dependência adicional de roteamento nesta release.

### 8. Edge Functions reproduzíveis

Imports flutuantes de `@supabase/supabase-js@2` foram fixados em `2.57.4` nas Edge Functions, evitando alterações inesperadas causadas por upgrades implícitos.

### 9. Integridade das migrations

`npm run migrations:verify` compara todas as migrations SQL com `supabase/migrations.lock.json` por SHA-256. Uma migration ausente, modificada ou não registrada falha a verificação.

## Migration desta release

Arquivo:

`supabase/migrations/202609120001_v100_52_architecture_hardening.sql`

Ela adiciona índices de suporte às consultas paginadas e amplia a publicação Realtime de forma idempotente.

## Configuração de produção

Variáveis mínimas:

```env
VITE_DATA_MODE=supabase
VITE_SUPABASE_URL=https://SEU-PROJETO.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=SUA_CHAVE_PUBLICAVEL
```

Nunca coloque `service_role`, `sb_secret_*` ou outro segredo do backend em uma variável `VITE_*`.

## Sequência de deploy recomendada

1. Fazer backup do banco e confirmar a migration atual aplicada.
2. Aplicar `202609120001_v100_52_architecture_hardening.sql` no Supabase.
3. Executar `npm ci`.
4. Executar `npm run check`.
5. Publicar em ambiente de preview/staging.
6. Validar login, Leads, Pipeline, Agenda, automações e integrações.
7. Confirmar comportamento de uma conta com mais de 1.000 registros, se disponível.
8. Publicar produção.

## Rollback

O código da V100.52 pode ser revertido para a release anterior sem remover os índices adicionados. Os índices são aditivos e podem permanecer no banco sem alterar o modelo de dados.

A ampliação da publicação Realtime também é compatível com versões anteriores; em caso de rollback ela pode permanecer ativa. Se houver necessidade operacional de removê-la, faça isso separadamente no Supabase após confirmar quais tabelas a release anterior consumia.

## Dívida técnica intencionalmente não misturada nesta release

Esta release não tenta reescrever o `AppProvider`, dividir todo o CSS principal ou substituir a engine local de automação. Essas mudanças têm grande superfície de regressão e devem entrar em releases próprias após a estabilização da V100.52.

Próximas etapas recomendadas:

- V100.53: decomposição do estado e repositórios por domínio;
- V100.54: modularização do CSS e componentes maiores;
- V100.55: consultas orientadas a tela, agregações server-side e virtualização para bases muito grandes;
- suíte E2E com Playwright após o pipeline de dependências estar disponível no CI.
