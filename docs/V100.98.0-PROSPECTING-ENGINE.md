# V100.98.0 — Prospecting Engine

## Arquitetura

```text
Fonte
  ├─ Google Places (direto quando configurado)
  ├─ CNPJ (consulta individual)
  ├─ Instagram (assistido)
  ├─ RT_Capture / Extensão
  └─ CSV/JSON/Manual
        ↓
Provider Gateway
        ↓
Normalização
        ↓
Identidade + deduplicação
        ↓
RealTalent Data Layer
        ↓
Revisão / aprovação
        ↓
Lead → Pipeline → primeira atividade
```

### Local Linux

`vite.config.ts` expõe um gateway **somente no servidor Vite local**. A chave do Google é lida pelo processo Node e nunca é enviada ao bundle do navegador.

Variáveis opcionais:

```env
GOOGLE_MAPS_SERVER_KEY=
CNPJ_PROVIDER_BASE_URL=https://brasilapi.com.br/api/cnpj/v1
```

Sem a chave Google, o sistema rebaixa apenas Maps para modo assistido. O restante do CRM continua iniciando normalmente.

### Supabase

A função `prospecting-search` exige JWT e permissão de escrita no workspace. Ela registra buscas em `prospecting_batches` e eventos em `prospecting_events`.

Secret esperado:

```text
GOOGLE_MAPS_SERVER_KEY
```

### Google Places API (New)

O motor usa `places:searchText` com field mask explícita. O limite do CRM é 20 resultados por consulta direta. Dados do provider entram em `rawData` para rastreabilidade e passam pelo Data Layer antes de aprovação.

### CNPJ

A rota aceita apenas um CNPJ completo de 14 dígitos por chamada. O provider base é configurável; no protótipo o default é BrasilAPI. Não existe varredura sequencial ou descoberta em massa por CNPJ.

### Instagram

Permanece assistido: o CRM prepara a busca e aceita retorno por RT_Capture, arquivo ou captura manual. Isso evita representar como oficial uma capacidade de descoberta ampla que a API da rede não oferece para este fluxo.

## Critério de envio ao CRM

Busca externa não cria Lead automaticamente. O caminho continua:

1. Captura/importação;
2. análise automática;
3. correção de identidade/contato;
4. deduplicação;
5. aprovação humana;
6. definição de Pipeline/responsável/próxima atividade;
7. envio.
