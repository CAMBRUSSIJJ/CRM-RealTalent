# V101.9.3 — Canonical Commercial Model

## Contrato de autoridade

```text
Pessoa / ContactRecord
  → nome, telefone, e-mail, cargo, papel decisório, influência, consentimento

Empresa / CompanyRecord
  → nome empresarial, CNPJ, domínio/site, cidade/estado e identidade da conta

Oportunidade / OpportunityRecord
  → etapa, status, valor, owner, previsão de fechamento e forecast

Lead
  → projection de compatibilidade + contexto de prospecção
  → origem, temperatura, prioridade, tags, notas e dados operacionais ainda legados
```

## Pipeline de leitura

```text
Repository
   ↓
WorkspaceSnapshot
   ↓
Snapshot Safety
   ↓
CanonicalCommercialGraph
   ├─ resolve Person
   ├─ resolve Company
   ├─ resolve Opportunity
   ├─ detecta inconsistências
   └─ projeta Lead legado
   ↓
Core Metadata Foundation
   ↓
Universal View Engine / Universal Record Page / UI existente
```

O adapter retorna um novo snapshot. Os objetos canônicos e o snapshot recebido do repository não são modificados durante a projection de render.

## Resolução

A ordem de resolução é conservadora:

1. vínculo explícito (`primaryContactId`, `companyId`, `opportunityId`);
2. relação inversa (`leadIds`, `opportunity.leadId`, empresa da Pessoa/Oportunidade);
3. match de identidade quando não existe vínculo;
4. fallback legado acompanhado por warning.

Matches ambíguos geram diagnóstico e não são tratados silenciosamente como verdade estrutural.

## Escrita de compatibilidade

A V101.9.3 ainda mantém ações antigas que chamam `updateLead`. Para não inverter a autoridade:

```text
UI antiga → updateLead
             ↓
        Lead compatibility patch
             ↓
   canonical write-through
     ├─ Pessoa
     ├─ Empresa
     └─ Oportunidade
             ↓
       reconciliation
```

Isso permite migrar os módulos em etapas, sem exigir uma reescrita simultânea de todo o CRM.

## Supabase

A migration V101.9.3 substitui `sync_commercial_structure(uuid)` por uma implementação canonical-first. Registros canônicos existentes deixam de ser sobrescritos por valores antigos do Lead. Dados ausentes continuam podendo ser preenchidos a partir do Lead e registros canônicos inexistentes continuam sendo criados.

Ao final da função, o Lead é atualizado como projection das três autoridades canônicas.

## Inspector

