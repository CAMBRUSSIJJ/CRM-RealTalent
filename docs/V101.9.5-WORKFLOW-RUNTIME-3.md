# V101.9.5 — Workflow Runtime 3.0

## Objetivo

Transformar automações com espera e ramificação em execuções duráveis. O navegador deixa de ser responsável por manter timers ou retentativas vivas.

## Arquitetura

```text
Automation event / Domain Event
          ↓
workflowRuntimeRequired(rule)
          ↓
enqueue_workflow_execution()
          ↓
workflow_executions
          ↓
pg_cron → automation-runner (1 min)
          ↓
Workflow Runtime 3.0
  ├─ action
  ├─ wait → next_run_at
  ├─ branch_if
  ├─ retry/backoff
  ├─ idempotency
  └─ workflow_step_runs
          ↓
Global Event Bus / Realtime
          ↓
Automações → Runtime
```

## Compatibilidade

Regras sem `wait` ou `branch_if` continuam usando o executor imediato existente. Regras com controles de fluxo são enfileiradas no runtime persistente quando o repository está em modo Supabase. Isso reduz risco de migração big-bang.

## Persistência

`workflow_executions` guarda status, etapa atual, próxima retomada, tentativas, lock, idempotency key, correlação, input/contexto e último erro.

`workflow_step_runs` guarda cada ação/espera/branch, tentativas, resultado de condição, agendamento, input/output e erro.

## Scheduler

O cron do `automation-runner` passa a executar a cada minuto. Esperas são representadas por `status = waiting` e `next_run_at`, portanto continuam mesmo com o CRM fechado.

## Retry e locks

Execuções `running` com lock expirado retornam para `retrying`. Falhas usam backoff exponencial com teto de 60 minutos e `max_attempts` persistente.

## Idempotência

`enqueue_workflow_execution` usa `(organization_id, idempotency_key)` como restrição única. O mesmo evento lógico não cria duas execuções duráveis.

## UI e inspector

A página Automações possui a aba **Runtime**, com estados, próxima retomada, retry/cancel e detalhes das etapas. O console expõe:

```js
window.__REALTALENT_WORKFLOWS__.load(workspaceId)
```

## Admissão e segurança

A entrada no runtime ocorre somente depois dos mesmos gates de segurança das automações imediatas: condições, modo de simulação, cooldown, limite por lead/dia e `maxActionsPerRun`. Isso vale para eventos da UI, `automation_events` e `activity_overdue`.
