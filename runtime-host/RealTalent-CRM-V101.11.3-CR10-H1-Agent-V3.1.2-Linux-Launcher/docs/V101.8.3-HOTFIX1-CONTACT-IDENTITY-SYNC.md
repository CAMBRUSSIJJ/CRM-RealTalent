# V101.8.3-H1 — Contact Identity Sync

## Objetivo

Eliminar divergência entre a tela **Contatos** (`Lead`) e a pessoa principal da conta (`ContactRecord`) sem fundir os dois objetos.

## Modelo preservado

```text
Conta / CompanyRecord
├── Oportunidade / OpportunityRecord
├── Pessoas / ContactRecord
│   ├── pessoa principal
│   └── stakeholders secundários
└── Registro comercial / Lead
```

`ContactRecord` é a fonte estruturada para identidade da pessoa quando está ligado como `primaryContactId`. `Lead` continua sendo o agregado operacional do fluxo comercial.

## Campos sincronizados

```text
name
phone
email
jobTitle
decisionRole
influenceLevel
consentStatus
doNotContact
doNotContactReason
```

## Campos que não são sincronizados com a pessoa

```text
company / companyId
stageId / status
temperature / priority
ownerId / ownerName
value
nextActionAt / expectedCloseAt
notes
tags
origem, redes e endereço da conta
```

## Regras de conflito

Na primeira reconciliação de uma base antiga:

- um valor preenchido no `ContactRecord` é preservado;
- se o campo estruturado estiver vazio ou `unknown`, pode ser preenchido a partir do `Lead`;
- `doNotContact=true` nunca é removido durante a reconciliação automática;
- depois da reconciliação, edições explícitas em qualquer um dos dois lados são propagadas imediatamente;
- apenas o contato primário participa da sincronização.

## Local

A sincronização ocorre antes de `writeDatabase()`. `synchronizeStructureInDatabase()` também repara instalações existentes durante `initialize()` sem duplicar pessoas.

## Supabase

A camada cliente sincroniza os dois sentidos e a migration adiciona triggers bidirecionais. Os triggers usam `pg_trigger_depth()` para evitar recursão Lead → Contact → Lead.
